**Applies to:** current documentation on `main` after release v1.6.0 (tag `v1.6.0`, commit `54711fc9f7d788b31d24ddf5db6950f6544d914f`; Zenodo version DOI [10.5281/zenodo.22087911](https://doi.org/10.5281/zenodo.22087911), concept DOI [10.5281/zenodo.20143142](https://doi.org/10.5281/zenodo.20143142)).

**Does not change:** any experiment, result array, per-cell `.npz` file, result summary, preregistration file, lock hash, figure, paper source, paper PDF, Git tag, Git LFS object or Zenodo deposit. The papers and the v1.6.0 archive keep their original bytes. Where a paper's wording differs from this note, this note is the dated correction; no revised manuscript is issued here.

**Scientific authorship:** Santiago Maniches is the sole scientific author. This note was prepared with AI-assisted review of the public repository and the public Zenodo record. It is not independent peer review.

Each item below says what the archived evidence supports, what the earlier wording said, and what remains unresolved.

## 1. Preregistration locks: what is hashed, what runtime checks, what history cannot show

**Hash-locked files.** Three registrations have a SHA-256 lock that `scripts/ci/verify_prereg_locks.py` re-verifies in CI:

| File | SHA-256 (LF bytes) |
|---|---|
| `data/prereg/PRE_REGISTRATION_HOMOLOGY_CLIFF_v1.md` | `139f60129d4e73dfb13444c360cc80c5b48c217d9bc87b1bf4b48b06515bcc06` |
| `data/prereg/PRE_REGISTRATION_HOMOLOGY_CLIFF_ADDENDUM_FULLNULL.md` | `f3864d097a0c611d790e6fb15a42e7efb36b2d1b103be4ec1c4f28f99d1004dc` |
| `data/prereg/PRE_REGISTRATION_CROSS_FAMILY_10SEED_v1.md` | `204953efeb098f7004b5e82586d5db6f721439b0abe9d214256817679a7a6804` |

The cascade (`PRE_REGISTRATION_STRATIFIED_CASCADE_v1.md`) and Fisher-Rao (`PRE_REGISTRATION_FISHER_CLIFF_v1.md`) registrations, and the earlier `PRE_REGISTRATION*.md` drafts, have no hash lock.

**Runtime check.** There is one shared runtime check, `verify_prereg_hash()` in `code/harnesses/run_cliff.py`. It hashes only `PRE_REGISTRATION_HOMOLOGY_CLIFF_v1.md`. `run_cliff.py`, `run_cliff_fullnull.py`, `run_cascade.py` and `run_fisher.py` all call this same function. The full-null, cascade and Fisher harnesses therefore re-check the main registration, not their own registration files. The ten-seed runner `code/analyses/run_cross_family_partition_10seed.py` checks its locked input files against `MANIFEST.sha256.json` and the t30 embedding hash written in its registration. It does not hash the registration file itself at runtime; CI does.

**Ordering that public history cannot establish.** The first public commit (`47412c1`, 2026-04-12) already contains the main, full-null addendum, cascade and Fisher registrations. The same commit contains completed paper sources and PDFs and result summaries (`data/results_summaries/v3_final.txt` and others). The 9,360 per-cell results follow 40 minutes later in `b00fe26`. The public repository therefore cannot show that these four registrations were written or hashed before their experiments ran. The `April 10, 2026` lock time in the `run_cliff.py` docstring is an author statement, not a verifiable timestamp. Statements on current surfaces that these registrations were "committed before their corresponding experiments", "locked ... before any evaluation" or "hashed before the experiment ran" go beyond what public history establishes. They are corrected to this scope. No retrospective lock or timestamp is created.

**Ten-seed extension.** For the later cross-family ten-seed registration, public history is consistent with lock-before-run: it was added in commit `a6b98c7` (2026-08-18), and its result was committed in `9e9008d` (2026-08-24) after GitHub Actions run `32692013434`. Git commit dates are recorded by the committer. This is ordering evidence, not an external timestamp anchor.

## 2. What the v1.6.0 Zenodo ZIP contains

The examined file is `smaniches/homology-cliff-v1.6.0.zip` from Zenodo record `22087911`: 10,105,601 bytes, MD5 `a2f3a4109ffd004566f7eddc72498582` (matches Zenodo's declared checksum), SHA-256 `ab0d8bbedeeca1f81cea7f439a1cbb0ebf91ab9d26f5945fbcdd67edc3829098`. It has 9,501 files. **9,365 of them are Git LFS pointer files, not the payload bytes.** Of these:

- 9,360 are the per-cell result files under `data/cells/`: 3,000 main, 3,000 negctrl, 3,000 fullnull, 180 cascade and 180 fisher.
- 5 are other payloads: `data/embeddings/embeddings_t6.npy`, `embeddings_t12.npy`, `embeddings_t30.npy`, `data/annotations/proteins_25k_pfam.json` and `data/sequences/proteins_25k_sequences.json`.

Together the pointers declare 187,505,260 payload bytes. A pointer records the SHA-256 OID and size of its payload, so it can identify and verify those bytes, but it is not those bytes. The v1.6.0 Zenodo archive therefore does not by itself let anyone recompute per-cell results. Committed summaries, PDFs and the other 136 regular files are present as real bytes.

This finding covers only the v1.6.0 ZIP inspected here. It does not say that the data are lost, and it does not say that other versions have exactly the same contents.

**Availability check, 2026-10-15 (read-only).** The public GitHub LFS batch endpoint for `smaniches/homology-cliff` returned a download action for all 9,365 OIDs referenced by the ZIP. Those 9,365 OIDs are identical to the LFS OIDs on current `main`. A stratified sample of 7 objects was downloaded and matched its OID and size: one cell from each of the five cell families, plus the sequences and Pfam annotation payloads. The remaining 9,358 objects are advertised as available but were not byte-verified. No new deposit or companion archive has been made.

## 3. Scope of 0.8905 and +47%

The learned-projection values come from the 10-seed means in `data/results_summaries/pooled_f1_summary.json`. They apply to **t30, R=1000, k=25**:

| Configuration | Learned pooled F1 | Cosine pooled F1 | Learned distant F1 | Cosine distant F1 | Relative distant change |
|---|---:|---:|---:|---:|---:|
| t30, R=1000, k=25 | 0.8905 | 0.8476 | 0.1770 | 0.1203 | +47.1% |
| t30, R=1000, k=5 | 0.8960 | 0.8827 | 0.1632 | 0.1617 | +0.9% |
| t30, R=500, k=25 | 0.8846 | 0.8290 | 0.2020 | 0.1205 | +67.6% |
| t30, R=500, k=5 | 0.8867 | 0.8624 | 0.1997 | 0.1448 | +37.9% |

0.8905 and +47% are correctly computed for t30, R=1000, k=25. The **+16% (t6) / +33% (t12) / +47% (t30)** series also refers to R=1000, k=25. "+47% at the largest scale" without the panel size and k does not describe other t30 configurations.

**Withdrawn superlative:** 0.8905 is **not** the highest pooled F1 in the archived summaries. In the 90-group archived pooled summary (R in {500, 1000}, k in {5, 25}), the learned projection at t30, R=1000, k=5 has 0.8960. The statements "best in 3000-cell factorial" and "the highest value observed anywhere in the 3000-cell factorial" are withdrawn. Pooled F1 was not recomputed here over all 300 main-factorial groups, because that needs the LFS cell payloads.

## 4. Paper 5 single-seed table: correction from archived per-case fields (2026-10-26)

The original Paper 5 single-seed table (panel seed `20260410`) includes two
incorrectly labelled counts. The published manuscript shows **36** for
"query Pfam known" and **20** for "at least one positive-voter Pfam known".
The first number cannot be reproduced under the declared predicate; the
second is the **joint evaluability count**, not the number with voter Pfam
known alone. The original intended unpublished calculation cannot be inferred.

The following **replacement table** defines every denominator and predicate
using `data/results_summaries/cross_family_partition.json` (41 per-case rows).
The seed `20260410` row in `cross_family_partition_10seed.json` independently
records the same per-case flags and aggregate counts:

| Quantity | Defined predicate over archived `detail` | Correct count |
|---|---|---:|
| Distant false positives | all rows in `detail` | **41** |
| Query Pfam known | `q_pfam_known` is true | **20** |
| At least one positive-voter Pfam known | `any_nbr_pfam_known` is true | **41** |
| Evaluable (both Pfam sets known) | both flags true | **20** |
| Within-family, among evaluable | `status == WITHIN_FAMILY` and both flags true | **0** |
| Cross-family, among evaluable | `status == CROSS_FAMILY` and both flags true | **20** |

The original **36** should not be cited as supported evidence. The
original **20** in the voter-known row should instead be read as the
joint evaluable denominator, *not* the voter-known marginal. This resolves
the numerical attribution under explicit, testable definitions; it does
not reconstruct the original author's intended filter for the two labels.

The primary 20/20 evaluable cross-family result, its per-seed Wilson
interval, and the later ten-seed confirmation are unaffected. The original
published v1.6.0 PDF, LaTeX, Zenodo deposit, result data, and historical
commits are preserved. This dated section is the public **corrigendum**
for the two descriptive table rows; it is not a revised manuscript.

## 5. Causal-exclusion wording

Paper 5 itself states that the cross-family result is "not categorical". It says the Mapper localization is "consistent with, but does not prove, an embedding-space explanation". It also says the ten-seed result "does not rule out benefit for a particular query or a different family ontology". Two current summary phrases were stronger than this:

- README read-order note: "Paper 5 shows why the fix has to be embedding-space rather than panel-side."
- Website limitations card: "The cross-family mechanism is at n=20 evaluable cases at one seed". This presents a mechanism and predates the ten-seed confirmation.

Both are replaced with Paper 5's qualified wording. The measured results are preserved: cross-family predominance in all ten preregistered seeds (median 1.000, range 0.962-1.000, 2 within-family appearances), the four rejected rescues, and all negative experiments.
